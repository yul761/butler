# BTL-190：待你决定、Butler 总控、换新不丢对话、实况窗口（设计）

来源：2026-11-12 用户在 BTL-190 里提出的 8 点。用户授权按我的判断决定，一路做到发新版（1.8.0），不再逐条确认。

## 调查结论（为什么要改）

1. **后台命令误报。** `activity-parse.ts` 只有看到 `queue-operation` 里的 `<task-notification>` 才认为后台任务结束。Claude 用 `TaskStop`（旧名 `KillShell`）停掉的任务从来不会有这条通知，于是一直挂着「后台 git push · 14 小时」。session 用 `--resume` 重开时，`TranscriptTail` 会重放最后 4MB，旧任务带着旧时间回来。本机 `~/.claude/projects` 里有 19 个这样的幽灵任务，查过的 12 个全是 `TaskStop` 停的。stuck 判断在这个基础上又会把它报成「卡住」，于是进了「需要你」。
2. **「需要你」不准、会重复。** 一条回复算不算「需要你」，全靠 Haiku 判断最后 1500 字，判断失败时只要以问号结尾就算（`needs-you.ts:81`）。于是「要我继续吗？」这种只是在等下一条命令的回复也被算进去。总控和子 session 各出各的行，没有去重。
3. **子 session 的决定被挤掉。** 子 session 没有办法把消息交回总控（只能等总控轮询 `list_sessions`），也没有「这是要用户决定的事」这种结构。总控页只有终端，要决定的事跟着对话往上滚。
4. **epic 不能一路开工。** epic 能 `create_feature`，但打不开 feature 的总控（`epic-design.md:13,44`：feature 总控只能用户自己打开）。
5. **没有比 epic 更高一层的视角。** 数据都在（`pr_watch` 表有 `all()`），但没有作用域能跨 epic 看。
6. **换新丢对话、接上后停住。**
   - 换新后接着做的那句话（`strings.ts:223`）明确写了「然后等用户的下一条指令，不要自己开始新的工作」，所以 session 停住是按原设计。
   - 收进记忆的 handoff 只有「状态 + 做完的事 + 下一步」，最近几轮对话没处放。
   - 写完 handoff 以后，Butler 不等记忆同步完（`void memory.syncTicket`）就 `/clear`，有可能 recall 到的还是上一份。
7. **「现在」页不准。** 顶上的「在跑」数的是开着终端的 session，不是真在干活的。有 PR 开着的已停 session 也算「进行中」。活动每 10 秒才从 transcript 读一次，UserPromptSubmit 后最多 10 秒还显示「停下」。整个界面没有任何动画或实时信号。
8. **session 清理。** 「隐藏」的 session 只是数据库里一行，终端已经退出，不占内存。真正占内存的是开着终端、在那里闲着的 claude 进程（每个几百 MB）。
9. **总控派的第一条任务送不进去（后来追加）。** 在本机用真的 claude（2.1.322）跑了 13 次。在已信任的文件夹里，任务每次都送进去了：长任务、MCP 启动慢、SessionStart hook 慢、粘贴后立刻回车、三个同时开，都没问题。claude 会收下提前到的输入。问题出在 `dialogShowing`（`pty-manager.ts`）认不出新版的信任对话框：
   - 新版在词和词之间用光标跳列，不打空格。去掉控制序列以后变成 `isthisaprojectyoucreatedoroneyoutrust?`、`❯no,exit / yes,itrustthisfolder`，带空格的标记一个都对不上。
   - **默默杀掉。** SessionStart 要等用户接受信任以后才来。子 session 开在还没信任的目录里（`~/Code-features/*` 的 worktree 是一个个信任的）时，60 秒后 `deliver` 当它已经启动，没看到对话框，就粘贴、回车。默认选项是「No, exit」，claude 随即退出，`deliver` 却已经返回 `sent`，日志里什么都没有。
   - **接受以后挂住。** 用户挪动选项时，对话框用真的空格重画了一遍。之后的欢迎界面是零碎画出来的，旧对话框文字一直留在最后 1000 个字符里，`deliver` 一直等到 300 秒超时。
   - 测试没发现，是因为测试里的对话框用的是旧文字、真空格，后面还补了 1200 个「─」把它推出去。

## 决定

### 1. 后台任务（修 bug）

- 后台任务也在这些情况下算结束：
  - 看到 `TaskStop` / `KillShell` 的 tool_result（`toolUseResult.task_id` 或 `shell_id` 对上）；
  - `user` / `attachment` 条目里带有这个任务 id 的 `<task-notification>`。
- 开始时间早于当前终端打开时间（`pty.openedAt`）的后台任务一律丢掉。后台 shell 活不过它的 claude 进程，所以这些任务一定已经结束了。
- 后台任务只有在终端的进程树里还有 shell 子进程时，才参与 stuck 判断。找不到子进程就当已经结束。
- 测试覆盖：TaskStop、KillShell、user 条目里的通知、早于终端打开的任务、没有子进程的任务。

### 2+3. 待你决定（一个结构化的收件箱）

- **两个新的 MCP 工具，所有 Butler session 都有**（ticket、feature 总控、epic、Butler 总控）：
  - `ask_user(question, options?, context?)`：把一件要用户拍板的事记成一条「待你决定」，然后这一轮结束。
  - `report(text, kind?)`：子 session 把进展交给总控和用户。`kind` 可以是 `progress`、`done` 或 `blocked`。
- **存储。** 新表 `inbox_items`：id、kind（`decision` / `report`）、session_id、ticket_key、feature_id、epic_id、text、options（JSON）、context、status（`pending` / `answered` / `dismissed` / `superseded`）、answer、created_at、resolved_at。
- **回答。**
  - 用户在卡片上选一个选项或打字回答后，Butler 用 `DeliveryGuard` + `PtyManager.deliver` 把「你问的『…』，用户的回答：…」送进提问的 session，然后标成 `answered`。
  - 用户也可以直接在终端里回答：提问的 session 收到 UserPromptSubmit 后，它的待定条目自动标成 `answered`。
- **汇报送给总控。** 子 session 的 `report` 除了存下来，还用 `DeliveryGuard` 送进它所属总控的终端（feature 总控，没有就送 epic 总控），等总控停下、用户没在打字时才送。这样总控不用轮询也知道子 session 做完了。kind 为 `progress` 的汇报只存不送，避免刷屏。
- **「需要你」只算真要你拍板的事**，来源按优先级：
  1. 权限确认、AskUserQuestion、ExitPlanMode（照旧）；
  2. 未决的 `ask_user` 条目，每条一行，说的就是那个问题；
  3. 真的卡住（第 1 点修好以后才可信）；
  4. Haiku 判断。它只是没用 `ask_user` 时的退路。提示词改严：问「要我继续吗」「还有别的吗」「下一步做什么」都算等下一条命令，不算需要你。判断失败就不算，不再看问号。
- **去重。**
  - 一个 session 自己有未决的 `ask_user` 时，它的 Haiku 行不再出现。
  - 总控所管范围里有子 session 的未决条目时，总控自己的 Haiku 行也不出现，因为它大多是在转述同一件事。
  - session 说明里告诉总控：子 session 已经用 `ask_user` 提出的事，不要再问用户一遍。
- **界面。** feature 页和 epic 页在终端上面加两栏并排：
  - 左边「汇报」：子 session 的 report 按时间倒序，标明哪个 session、什么时候；
  - 右边「待你决定」：卡片，显示问题、背景、选项按钮、回答框、「去终端」、「不用了」。没有内容时整块收起。
  - 「现在」页的「需要你」也显示 `ask_user` 的卡片，能直接回答。
- **实现时定下的细节**（和上面不一样或者上面没说的）：
  - 工具：ticket session 原来没有 butler-sessions，现在也挂上，但只有 `ask_user` 和 `report` 两个工具（环境变量 `BUTLER_MEMBER=1`），别的工具拒绝。工具名所有 session 一样。调用方必须能按 `BUTLER_SESSION` 找到、而且在这个 scope 里（ticket 的 session 不能冒充 feature / epic 的），找不到就拒绝。`question` 最多 1000 字、`context` 4000 字、`options` 最多 6 个各 200 字、`report` 4000 字；`kind` 默认 `progress`。
  - 存储：多一列 `report_kind`。session_id 存提问时的 id，显示和比较时都换成链上的 head，换新过的 session 照样认得。汇报借用 status：`pending` 是还要送给总控，`answered` 是送到了，`dismissed` 是不用送（progress、epic 自己的汇报、作者已经不在、超过 6 小时还没送出去）。
  - 同一个 session 再问一模一样的问题时，旧的那条标成 `superseded`。
  - 回答：卡片上答了以后先记下答案（status 还是 `pending`，卡片写明「已回答，等它停下来再送」），提问的 session 停下来（Stop）或者每个活动 tick 时再送，送到才标 `answered`。送回答用的 guard 不看「需要你」（未决的 ask_user 本身就算），别的检查（忙、屏幕上有对话框、用户在打字、有草稿、在换新）照常。同一个 session 有几条答案时合成一条消息送。终端关着时答案留着，打开后再送。
  - Butler 自己送回答引起的那次 UserPromptSubmit 只结束这次送的条目，不把别的未决条目一起算答过。
  - 汇报的去向：只送给开着终端的总控，从近到远找第一个——ticket session 先找它的 ticket 总控，再 feature 总控，再 epic session；ticket 总控和修复 session 找 feature 总控，再 epic session；feature 总控找 epic session。epic session 自己的汇报只存不送。几条汇报合成一条消息送（按 data 而不是指令的口吻），最多约 7000 字一批。
  - 有未决 ask_user（包括答了还没送到的）的 session：CI 结果、合并通知不往里贴，不自动换新，不闲置关闭。
  - 去重在「现在」页拼数据时做（`buildNowView`），Haiku 照旧判断。总控的范围：ticket 总控管这个 ticket，feature 总控管这个 feature（含它的 ticket），epic session 管整个 epic。停在确认上的照样先显示确认。
  - Haiku 说需要你却没给理由时，照旧用最后一句当理由；判断失败就是不需要你。
  - epic 页的两栏显示整个 epic 的条目（含它下面的 feature 和 ticket），feature 页显示这个 feature 和它的 ticket 的。「去终端」：本页面上的 session 就地切过去（终端关着就打开），别的跳到它的页面。汇报栏最多显示最近 30 条。
  - 侧栏「需要你」的数 = 需要你的行 + 未决的「待你决定」（每条算一件）。

### 4. epic 一路开工

- epic 新增工具 `start_feature(feature, instructions?)`，`create_feature` 也新增参数 `start: boolean`。效果是打开这个 feature 的总控，把规划（brief）和「按规划建 ticket、开 session 开工」一起作为第一条消息发过去。
- 限额：一个 epic 同时最多 4 个 feature 总控在跑（`MAX_RUNNING_FEATURES_PER_EPIC`）。每个 feature 照旧最多 8 个终端。
- epic 设计文档里「feature 总控只能用户打开」那一条改成：用户打开或 epic 用 `start_feature` 打开。
- **实现时定下的细节**（和上面不一样或者上面没说的）：
  - `feature` 是 `list_features` 里的名字或 id（MCP 那边把数字 id 转成字符串）。只在这个 epic 未归档的 feature 里找：全是数字时先按 id，再按名字（不分大小写、去掉首尾空白）；找不到时错误里列出现有的 feature。`instructions` 最多 2000 字符（`START_INSTRUCTIONS_LIMIT`），空白当作没给。
  - 只在用户同意开工后调用：写在工具说明和 epic 的 session 说明里，Butler 不另外拦。epic session 的 session 说明从 `coordinator` 分出来，新的 `GuideKind = "epic"`：多一段 `start_feature` 的用法，保留「子 session 的问题和汇报 Butler 已经处理了」，去掉 `start_session` 选模型那一段（epic 不开 ticket 的 session）。
  - 开哪个总控：和用户点进 feature 一样，接着最近一个没隐藏、没被换掉的总控（包括闲置时自动关掉的），没有才新开。返回里 `started` 是 `opened`（新开）或 `resumed`（恢复）。
  - 第一条消息（新开的和恢复的总控一样）：规划还没发过（`briefSentAt` 为空）时，发开工版的完整规划（brief、整体规划、以往的决定、其他 feature），说明换成「不用等用户确认，按规划用 create_ticket 建 ticket、用 start_session 开子 session；需要用户决定的用 ask_user，做完或卡住用 report」，发到了才记 `briefSentAt`。已经发过（之前用户开过总控），发一条短的开工消息，附上 brief，不再改 `briefSentAt`。恢复的总控只有 epic 让它开工时才发，用户自己恢复照旧什么都不发。`instructions` 是 epic session 写给总控的话，放在数据标签前面，超长截断只截后面的数据。
  - 总控已经开着时（spec 留的两个选项里选了 DeliveryGuard + deliver）：不开第二个。没给 `instructions` 就什么都不发，返回 `already_running` 和提示；给了就过和递汇报同一道 guard（`deliveryGuard`），过了用 `pty.deliver`（带 recheck）把一条只含 `instructions` 的消息送进去，返回 `sent`，不等它送到，没送到只记日志；guard 不过（忙、屏幕上有确认、在等用户回答、用户在打字、有草稿）返回错误并说明原因，让 epic 稍后再试。
  - 限额：数这个 epic 下未归档、有终端在跑总控的 feature（`SessionService.runningCoordinator`，现在是公开的），加上正在打开的；到 4 个时返回错误并列出是哪几个。要开的这个已经在跑时不算新开，照样走上一条。feature 自己的终端到 8 个时也拒绝。同一个 feature 正在打开时再调返回 `starting`，不开第二个。
  - feature 没有 brief（比如移进来的）又没给 `instructions` 时拒绝，让 epic 写清楚要它做什么；给了 `instructions` 就照开。
  - `create_feature` 带 `start: true`：先照常建，再走 `start_feature` 同一条路。开不了（到上限、找不到 claude……）时 feature 照样建好，返回 `ok`，`started: false` 和原因，让 epic 之后再用 `start_feature`。
  - 开工的总控做完或卡住时的汇报，沿用第 2+3 点：feature 总控的 `report` 送给开着终端的 epic session，这里不用另加。

### 5. Butler 总控

- 新作用域 `butler`，全局只有一个。
  - 工作目录：`~/.butler/workspaces/_butler`；
  - 记忆：用 `butler-workspace`；
  - session 说明：新的 `GuideKind = "butler"`。
- 侧边栏最上面新增入口「Butler 总控」，页面就是一个 `SessionArea`，上面放同样的「汇报 / 待你决定」两栏，显示全局内容。
- 工具，只读为主：
  - `list_epics`、`list_features`（全部，带 epic）、`list_tickets`（可以按 feature 或 epic 筛）、`list_prs`（来自 `pr_watch`：状态、review、CI，带所属 ticket、feature、epic）；
  - `list_sessions`（所有开着的 Butler session，带活动和「需要你」）、`session_activity`、`list_inbox`（未决的待你决定和最近的汇报）；
  - `send_message(session, text)`：给某个 epic 或 feature 总控发一条话，走 `DeliveryGuard`。用于跨 epic 协调。
  - `refresh_session`。
- 不能建或删任何东西，那些留给 epic 和 feature 总控。
- 每天早上巡检：设置项「每天几点让 Butler 总控巡检一次」，默认关闭。打开后到点开启（或复用）Butler 总控 session，发一条巡检指令：看所有 PR、CI 和待你决定，把需要用户做的事用 `ask_user` 列出来。

### 6. 换新不丢对话、接上后继续

- **对话尾巴缓存。**
  - 输入 `/clear` 之前，Butler 自己读旧的 transcript，取最近的对话，写进 `~/.butler/refresh/<session-id>.md`。不调用模型，不花 token。
  - 取法：从最后一次 handoff 之前开始往后取，最多 8 轮用户和助手的文字；工具调用每次只记一行名字和参数摘要；总共最多 12000 字，超出时去掉最旧的。
  - 同时在 sessions 表记下这个文件。下一次换新覆盖它，session 删除时一起删掉。
- **等记忆真的写完。** handoff 收进来以后，等 `memory.idle()`（最多 60 秒）再 `/clear`。
- **接着做的那句话改成：** 用 recall 调出最新的 handoff，再读一下 `<文件路径>` 里换新前的最近对话，然后接着做换新前正在做的事。如果换新前是在等用户、等 CI 或者等子 session，就说一句在等什么，然后继续等。
- 去掉换新后对下一条回复的「需要你」屏蔽（`suppressNext`）。session 现在会接着干活，屏蔽会把它干完后真要问的那一条也吞掉。第 2 点的判断改严之后，「我在等 CI」这种回复本来就不会被算成需要你。

### 7. 实况窗口

- **「现在」页最上面加「实况」**，样子照 butler.statecore.io 的头图：
  - 中间是 Butler 核心卡片，显示正在干活的 session 数和最近的记忆读写；
  - 四周是正在干活的 session 小终端卡片，显示 ticket 号、仓库、状态药丸，以及最近 3 行工具调用；
  - 卡片和核心之间连虚线：session 写记忆时一个蓝色光点从卡片流向核心，读记忆时一个绿色光点从核心流向卡片；
  - 正在干活时状态药丸闪烁；在等你决定时卡片边框变黄，顶上冒出「需要你 · N」；
  - 停下的 session 不出现在实况里，只在下面的列表里。没人在干活时显示「现在没有正在进行的工作」。
- **实时信号。**
  - ActivityMonitor 对开着的 transcript 用 `fs.watch`（去抖 300ms，保留 10 秒的 tick 当退路）。
  - 每看到一个新的 tool_use，就通过新的 IPC `activity:event` 推一条 `{sessionId, at, kind: "tool" | "memory-write" | "memory-read" | "turn-start" | "turn-end", label}`。记忆读写按工具名识别：`*__remember`、`*__handoff` 算写，`*__recall`、`*__facts`、`*__why` 算读。
  - UserPromptSubmit 时立刻重读活动。
- **数字改准。**
  - 「在干活」只数正在干活的 session：思考中、跑工具、后台命令。
  - 已停的 session 不因为有 PR 开着就算进行中，PR 和 CI 只显示在行上。
- 动画只用 CSS（`@keyframes` 和 transition），尊重 `prefers-reduced-motion`，配色跟随浅色和深色主题。

### 8. 清理 session

- **闲置自动关闭。** 新设置 `idleCloseMinutes`，默认 180，0 表示关掉。满足下面全部条件的 Butler session 会被关闭：
  - 终端开着，停下超过这个时间；
  - `DeliveryGuard` 通过，没有「需要你」，没有未决的 `ask_user`，没有后台任务，不在换新中；
  - 如果是总控，它管的子 session 都没在干活。

  - 没在等 Butler 递消息：合并总控里没有它的等待者，它 ticket 的 PR 没有 CI 在跑（这些通知只递给开着的终端）；
  - 电脑睡着的时间不算闲置：醒来以后从头算。设置最短 10 分钟。

  关闭的做法：先走换新的 handoff 那一步（ticket 和 feature 用 `/handoff`，epic 和 Butler 总控用 handoff 工具），记忆写完以后再等 session 停下、没有后台任务、「需要你」判断完，然后结束终端（和 `end_session` 一样，以后还能恢复）。记忆关着时 ticket 和 feature 照样写 `/handoff`（存在 Butler 自己的库里，每日简报要用），epic 直接结束。

### 9. 交任务看真正的屏幕，并确认送到

- **按当前屏幕判断。** 每个终端在主进程里多挂一个 `@xterm/headless`（和渲染进程同一版本，scrollback 0，跟着 resize）。对话框、权限确认、输入框都看它当前显示的那一屏，不再看输出流的最后 1000 个字符，屏幕上已经消失的旧文字不会再误判。
- **只看对话框会在的那一块。** 屏幕下方画着输入框（两条「─」线，中间第一行以「❯」开头，下面只剩几行提示）时就没有对话框，对话内容里出现「No, exit」「Do you want to proceed?」不算。没画输入框时只看最后一条线以下：启动对话框、权限确认、退出计划模式的提示都是顶替输入框、画在一条线下面的。
- **去掉空白再比。** 屏幕文字转小写、去掉所有空白以后再找标记，跟 claude 用空格还是光标跳列无关。启动对话框的标记：`itrustthisfolder`、`doyoutrust`、`trustthefiles`、`yes,proceed`、`no,exit`、`newmcpserver`、`mcpserversfound`、`usethisandallfuture`、`entertoconfirm`。权限确认的标记照旧，也去掉空白。`screenNeedsUser` 和活动监视器的权限判断一起换成看屏幕。
- **不靠盲等。** 等满 `startWaitMs` 还没有 SessionStart 时，照旧只在「屏幕上没有对话框」时才粘贴。现在这个判断可信了，不会再在信任对话框上按回车。
- **确认送到。** 回车以后最多等 10 秒，等这个终端的 UserPromptSubmit（`PtyManager.markSubmitted`，hook 里 `waiting: false` 那一路）：
  - 等到了就返回 `sent`；
  - 没等到，而且输入框里还留着这次粘贴（`[Pasted text` 或任务开头的字）、用户从粘贴以后没碰过这个终端、屏幕上没有对话框和权限确认，就再按一次回车，再等 10 秒；
  - 还是没等到，记一行日志「没确认送到」，照样返回 `sent`（东西已经写进去了，不重贴，免得发两遍）。
  - 回车写进去以后一律返回 `sent`，等的时候终端退出也是：返回 `exited` 的话调用方会当没送到，重开以后再送一遍。
  - `/clear` 这类斜杠命令不触发 UserPromptSubmit，不等确认。
- **测试。** 用探测时录下的真实字节流做回放：没信任时的对话框（不粘贴、不回车）；接受以后的重画（能交）；确认送到、补一次回车。
