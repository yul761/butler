# Butler UI 重做：设计

日期：2026-11-19 · 基于 v3.0.0（main bcf1df8）· 状态：问题已答完，等用户批准

能点的整体草图：`.superpowers/brainstorm/1247-1795150005/content/full-mockup.html`（用户已认可「按这个做」）。草图里的数据是编的，结构和文案以它为准。

---

## 1. 为什么要做

用户在单位试用 3.0.0 后，提了三个问题：

1. **新功能一下子加了很多，没有引导。** 首次启动向导只负责装好 claude 和 hook，结尾只有一句「点左侧新建 ticket 开始」。epic、feature、总控和 3.0 的新功能都没讲。3.0 新加的二十多个开关全部默认关闭，混在设置「常规」页大约 40 个开关里，也没标出哪些是新的。
2. **还是得去问 session「现在怎么样了」「这个 epic 下有没有能处理的 PR」。** 界面上信息很多，但互相对不上，也说不清「现在轮到谁」：
   - 同一个 PR 的状态显示在 7 个地方，用了 4 种算法。
   - 「卡住」有 3 种意思。
   - 大约 25 种状态标记共用 4 组颜色，同一个红色既表示 CI 挂了，也表示有人要求修改、高风险、费用熔断。
   - 首页的「需要你」只算 session 停下来问你的情况，PR 的状态一条都不算。
   - epic 行显示的进度是 AI 汇总的第一句话，可能是几个小时前写的。
3. **在讨论或问答时，Butler 会自动换新（handoff，然后 /clear），回答在终端里就看不到了，session 也不记得刚才答过什么。**

根本原因是：每加一个功能，界面就多一个页面、一个 tab、一组开关。整个界面按对象（epic / feature / ticket / session）和功能来组织，而不是按用户每天要做的三件事：**看现在怎么样、看哪些轮到我、和 agent 说话。**

用户的总体感受是：「有用的信息很多，但一下子给得太多了。」

## 2. 目标、非目标、反目标

**目标**
- 打开 Butler 后，首页一眼就能看出「有没有轮到我的事」。只要首页没有红条，就不用去问任何 session。
- 整个 app 只用一套状态说法，格式是「谁该动 + 一句话」。首页、epic 页、ticket 页对同一件事说的是同一句话。
- 信息分层：每页的默认层只回答一个问题、只放少量信息；次要信息放进 tab，想看的时候再切过去。
- 问答和讨论的内容不随换新或 /clear 消失，可以往回翻、可以搜索。session 换新之后也能想起刚才的问答。
- 新用户第一次打开时，知道 Butler 是干什么的、有哪三种开工方式、3.0 的功能分别会替自己做什么。

**非目标**
- 不换技术栈，不重写数据层。Electron、React、SQLite、现有的 IPC 和大部分组件都沿用。
- 不改 Butler 的后台行为，包括 CI 转发、review 转发、栈、预审、休眠、自动接活。只是把它们已经知道的东西显示出来。只有两个例外：一是换新流程要改（见 §5.4），二是要新加一路「请你 review」的查询（见 §5.1）。
- 不做多用户或团队视图。

**反目标**（就算功能都能用，出现下面这些也算失败）
- 默认层又堆满了信息，需要滚动才能看完。
- 同一件事在两个页面上说法不同。
- 为了保住屏幕上的回答，去拦着不让换新，导致上下文越撑越大。
- 讨论的内容只存在 Claude Code 的对话文件里。那个文件随时可能被清理或改格式，Butler 自己没有一份。

## 3. 约束

- 用户这周不开发（周额度快用完了），这份文档只做设计准备。估计开发要十几个小时。
- 3.0 的功能默认全部关闭，这一点不变。Butler 默认不替用户对外做任何事。
- 界面中英双语（`strings.ts` / `strings-en.ts`），新文案两边都要有。
- 换新的触发阈值（上下文到 150k 且 session 停下）不变。

## 4. 考虑过的做法

### 4.1 改到什么程度

| 做法 | 取舍 | 结论 |
|---|---|---|
| 在现有页面上修补：统一颜色、把 PR 状态加进「需要你」 | 最省事，但结构不变，下次加功能还会继续堆 | 不选 |
| **重做信息架构，组件和数据沿用** | 首页是什么、信息放在哪一层、状态怎么说，这些全部重定；底层的数据和组件大多能直接接上 | **选这个** |
| 连技术栈一起重写 | 成本高，而且问题不在技术栈 | 不选 |

### 4.2 首页

- **A. 「轮到你」清单**：从上到下排列轮到你的事，每条带一个动作按钮。**用户选了这个。**
- B. 看板，四列：卡片太窄，写不下「为什么」，按钮也挤。

### 4.3 session 页的对话区

- A. 两个 tab，一个是「记录」，一个是「问一下」：结构清楚，但同一件事要在两个 tab 之间来回找。
- **B. 一条时间线**：分叉出去的讨论用黄框嵌在时间线里，输入框下面选这句话发给谁。**用户选了这个。**

另外，用户要求「问答记录」和「单独讨论」都做：

- 每个 session 旁边都有一份完整记录，不随 /clear 消失。
- 单独讨论从开发 session 分叉出来，不占开发 session 的上下文。

### 4.4 epic 和 feature 页

- **A. 和首页用同一套**：**用户选了这个**，并要求按分层原则再精简，次要信息放进 tab。
- B. 结构表：保留下来，作为 epic 页的「全部 ticket」tab。

### 4.5 讨论内容存在哪里

- 只从 Claude Code 的 JSONL 读，沿 `replaced_by` 链串起来：不另外存，但完全依赖外部文件。
- **Butler 自己另存一份**：这是用户的要求，原话是「判断为问答的对话，另存一份到 Butler 里」。这样换新和 clear 照常进行，右侧的显示和往回查都不受影响。

## 5. 定下来的设计

### 5.1 统一的状态模型：「谁该动 + 一句话」

每个 ticket（以及它的 PR）在任何时刻都只有一个状态。状态由数据直接算出来，不用 AI 生成：

| 谁该动 | 例子（这一句话在全 app 通用） | 颜色 |
|---|---|---|
| **你** · 要你回答 | session 停下来问你问题 | 红 |
| **你** · 可以合并 | 你的 PR：CI 绿、review 已通过或者不需要 review、没有冲突 | 绿 |
| **你** · 要你 review | 你是被请的 reviewer | 红 |
| **你** · 卡住了 | session 停了，又不是在问你（stuck-judge 判定） | 紫 |
| **agent** | 「#53 CI 挂了，已经送给它，正在修」「有冲突，在 rebase」「在写测试」 | 蓝 |
| **外部** | 「CI 在跑」「等 bob review」 | 灰 |
| **合了** / **没开始** | — | 绿（浅）/ 灰 |

- 这一套替换掉现在 7 处显示、4 种算法的 PR 状态，也替换掉「卡住」的 3 种意思。颜色只表示「谁该动」，不再表示严重程度。风险、费用熔断这类信息作为文字写在那一句话里。
- 「agent 在处理」和「轮到你」的区别要靠后台已有的数据来判断：
  - `ci-delivery.ts` 里的 `pickRecipient` 和 `ticket_prs.delivered_key`：CI 失败结果送给了哪个 session、有没有送到。
  - `hibernation.ts` 里每个 session 在等什么，分四类：等你、等 CI、等 review、空闲。

  这些现在只在 main 进程里，要通过 IPC 传给界面。现在的 `waitingOnOf` 按 author / ci / reviewers 分类（`src/shared/progress.ts:57-76`），在 Butler 的场景里分不出 agent 和用户，要替换掉。
- **「要你 review」**（用户定的：要进首页）：别人请你 review 的 PR，不管在不在 ticket 里，都进「轮到你」。后台要新加一路查询（下面是我定的频率）：
  - 每一轮只调一次 `gh search prs --review-requested=@me --state=open`。一次调用就覆盖所有仓库，GitHub 搜索接口每分钟允许 30 次，这个量可以忽略。
  - 平时每 5 分钟查一次，和现在 PR 的慢速轮询一样（`PR_SLOW_MS`）。
  - 窗口切到前台、或者打开首页时，如果离上次查已经超过 1 分钟，就马上补查一次。
  - 电脑空闲或锁屏时放慢到 15 分钟一次。
  - 默认查你账号能看到的所有仓库，设置里可以改成只查 Butler 登记过的仓库。
  - 查到的 PR 再按现有的慢速节奏读详情。你交了 review 以后它就从首页消失；如果对方再次请你 review，会重新出现。
  - 卡片上的位置写成「仓库#号 · 作者 · 请你多久了」。这类 PR 不属于任何 epic，所以不写 epic › feature › ticket。
- **「可以合并」现在完全没有判断，要新补。** ticket 的 PR 都是 agent 用用户自己的 gh 账号开的，作者就是「你」，所以不用另外认定「你」是谁。
- epic 行和 feature 的进度改成数字加进度条，比如「15 个里合了 9 个」。不再取 AI 汇总的第一句。
- **「卡住了」只指一种情况**（我定的）：session 自己说做不下去了，或者在跑却长时间没有动静。具体来源有三个：
  - needs-you 判出的 `stuck` 或 `missing_info`
  - 子 session 交来的 blocked 汇报
  - stuck-tracker 判定的「在跑但长时间没输出」

  ticket 被手动标成 blocked 的，也算这一类。
- **状态按 PR 算，ticket 取最急的那个**（我定的）。急的顺序是：你 > agent > 外部 > 合了 / 没开始。首页每个要你处理的 PR 各出一张卡，ticket 那句话说最急的那个 PR；如果不止一个，后面加一句「另有 1 个 PR 在等 CI」。没有 PR 的 ticket，就按它的 session 来算。

### 5.2 信息分层（总原则，用户定的）

1. 一页只回答一个问题，默认层不用滚动就能看完。
2. 不用你动手的东西，只显示成一个数字，或者放进默认折起来的一块。
3. 一种状态只有一种说法（见 §5.1）。
4. tab 记住你上次看的那个。从「轮到你」点进去时，直接落在能处理这件事的 tab 上（对话或终端）。
5. 页面是空的时候，用一句话说明这一页是干什么的。这也是新用户引导的入口。

### 5.3 各个页面

以草图为准，下面是要点。

**侧栏**：从 13 个入口收成下面几个：

- 轮到你（带数字）
- 全部工作：树形，epic › feature › ticket，每一项带一个状态点和「轮到你」的数字
- 总控
- 「Butler 自己」一组：复盘与规矩、效果与花费、审计、设置
- 底部：防止休眠

进度页拆掉，内容并进首页和 epic 页。「未认领的 session」和「已归档」改成「全部工作」页上的两个按钮。

**首页（轮到你）**，从上到下：

- 一行标题：「N 件事轮到你」。
- 一句话带过其余的：「agent 在处理 5 个，在等 CI 或别人 2 个，今天合了 5 个。」
- 轮到你的事，每条一张卡片：类型标签、一句话、所在位置（epic › feature › ticket）、多久了，再加一到三个按钮。
  - 回答问题：直接给选项，比如「可以」「不行，先回测」，再加一个「去看看」。
  - 可以合并：「打开 PR」。
  - 卡住了：「去看看」「开修复 session」。
  - **Butler 要你点一下**（我加的第 5 类，紫色以外用琥珀色）：现在「现在」页上那些要用户动手的提醒，比如费用熔断暂停了等你点继续、评论等你确认分类、自动接活拿不准、栈冲突没交到 session、CI 结论半小时没送出去、claude 撞了限额或模型不可用、屏幕上的权限确认。每条都带原来的按钮。纯告知类的提醒（比如检查自动升级了、可以撤销）不上首页，放进「Butler 自己」相应页面的主层。
- 「各个 epic」小表，每个 epic 一行：一句状态、一条分色进度条、几件轮到你。单独的 ticket 也各占一行。
- 「进行中 N」，默认折起来。展开后每行是 ticket、谁（agent / CI / 某个人）、一句话、多久。

**全部工作**：放新建 ticket / feature / epic 的按钮，以及「已归档」「未认领的 session」两个入口。下面一张表，列是名字、谁该动、现在怎么样、进度。

**epic 页**（feature 页同构，范围小一层）：

- 默认 tab 是「概况」：一句进度（「15 个里合了 9 个 · 2 件轮到你」），一句最慢的地方，这个范围里轮到你的事，再加各个 feature 的进度卡片。
- 其他 tab：
  - 进行中
  - 全部 ticket：结构表，按 feature 分组，每个 ticket 一行，列是谁该动、现在怎么样、PR
  - 总控：session 页布局，左边终端、右边对话
  - AI 总结：标出生成时间，带「立即更新」
- 去掉现在的「汇报」和「待你决定」两个 tab。待你决定的事进「轮到你」，汇报进总控的对话区。
- 总控终端不再固定在页面下半截。

**ticket 页**：

- 默认 tab 是「概况」，依次是：
  - 一句状态（「#52 可以合并了 · 轮到你」）
  - 主按钮
  - agent 最后说的那句话
  - 一小块基本信息：分支、PR 走到哪个阶段、上下文用了多少；快到换新时提示「对话不会丢」
- 其他 tab：对话、终端、PR 详情（CI、review、风险、就绪 6 项、阶段、未处理的评论）、记录（handoff、记忆）。
- Claude 终端放在 tab 后面，这是用户提的。

**对话 tab**（选的是方案 B，一条时间线）：

- 所有说过的话按时间排在一起。换新的地方有一条分隔线，写着「14:32 换新了上下文 · handoff 已保存 · 对话已另存」，分隔线之前的内容还在。
- 分叉出去的讨论用黄框标出来，框上写「从开发 session 分出来，只读，不影响它」。框里有三个按钮：「按这个改 → 发给 session」「记进记忆」「接着问」。
- 顶部的筛选：全部、只看讨论、搜索。还有「并排显示终端」，切到左边终端、右边对话的布局。
- 输入框下面选这句话发给谁：「开发 session」或者「只问不改（分叉讨论）」。

**总控页**（侧栏里管所有 epic 的那个）：左边终端、右边对话。子 session 的 done / blocked 汇报按时间进对话区。

**Butler 自己**：每页先用一句话说明这页是什么，主层放一个最需要你看的东西（比如「4 条新规矩等你看一眼」），细节放进 tab。审计页没有内容时，用空状态说明「Butler 默认不替你对外做任何事」。

**设置**分四个 tab：

- 基本
- 功能：每个 3.0 功能一行，一句话说明它会替你做什么，带「3.0」标记和开关，默认全关。下面三点是我定的：
  - 不新加总开关，也不做迁移。每一行直接对应现有的全局开关；一行对应几个开关时，一起开、一起关。
  - 某个仓库或产品另有覆盖设置时，这一行下面注明「2 个仓库另有设置」，可以点进「高级」查看。
  - 打开「review 评论自动送回」不会顺带打开对外发评论这类开关。一句话说明里写清楚：「不对外发任何东西」。
- 高级：原来各组的细项，按功能分组，默认收起
- 健康检查

### 5.4 对话另存和换新

用户的要求：被判断为问答的对话，Butler 自己另存一份。这样换新和 clear 照常进行，右侧的显示和往回查都不受影响。

- **存什么**（用户定的）：所有对话都存，但只存双方说的话，加上时间、session id、`replaced_by` 链的根、是不是分叉讨论、是不是问答。程序运行的部分一律不存，比如跑了什么 bash、读了哪个文件。存下来的对话以后还可以拿来做分析。一段对话也就几 KB。
- **从哪来**：从 Claude Code 的 JSONL 增量读进来，可以复用 `transcript-watch.ts` 的去抖监视。分叉讨论是 Butler 自己发起的，直接写入。
- **问答怎么判断**：
  1. 先用规则判断：用户那句是问句（带问号，或者有「吗」「怎么」「为什么」之类的词），并且 agent 这一轮没有改文件、没有 commit、没有 push。
  2. 分叉讨论一律算问答。
  3. 规则判断不了的，交给 Haiku。
- **换新不再等用户**（用户定的）：右侧的对话区读的是 Butler 存的这份，不再跟着 session 走，所以换新照常进行，不用等用户看完。
- **换新之后**（我定的）：现在的 refresh-tail（`src/main/sessions/refresh-tail.ts`，存最近 8 轮，带工具调用摘要）**保留**，因为换新后的 session 要靠它知道刚改了什么、跑了什么。另外在恢复提示里**再加上**最近几段问答，从 Butler 自己存的那份里取。这样即使 refresh-tail 被下一次换新覆盖，问答也还在。
- **一个 ticket 有多个 session 时**（我定的）：对话按 session 的 `replaced_by` 链分开存，链的根作为主键。对话 tab 默认显示主 session。如果还有修复 session 或子 session，顶上加一个切换。「发给开发 session」发给当前显示的那个。
- **分叉讨论**：沿用 handoff 已经在用的分叉方式（`--resume --fork-session`），不碰开发 session。下面两点是我定的：
  - 讨论要能连续多轮，所以分叉出来的 session 留着，「接着问」就续这个分叉，不用每轮重新分叉。
  - 讨论可以读代码，但只给 Read、Grep、Glob 这类只读工具。

  点「按这个改」时，把讨论的结论（不是全文）作为一条消息发给开发 session。
- **分叉讨论怎么省钱**（用户说贵一些也能接受，但希望研究一下能不能借 StateCore 的记忆来省。下面是 2026-11-19 的调研）：
  - **实测**：本机 `~/.butler/app.db` 的 `session_usage` 里有 11 月 8 日到 19 日的 handoff 分叉记录。每次分叉第一轮都把整段上下文重新写进缓存（1 小时那档），写入量和读出量差不多。比如有一次写 113,386、读 112,810 个 token，没有一次命中开发 session 已有的缓存。原因是分叉时的参数和开发 session 不一样，缓存是按前缀逐字比对的，前缀一变就全部失效。不同之处包括 `--disallowedTools` 改了工具列表，还有 `--json-schema`、MCP 配置、模型路由。按 Opus 5.5 的价格算，开一个约 11 万 token 的分叉，大约 1 美元：1 小时档的缓存写入是 2 倍价，每百万 8 美元。用订阅的话，算的是额度。
  - **精简版**：分叉不复制完整上下文，而是新开一个只读 session，开头带上三样东西：
    - StateCore 的 recall，也就是这个 ticket 或 feature 的决定、约定和最新 handoff
    - Butler 自己存的最近几段对话（§5.4，只有说的话，没有工具调用）
    - 用户的问题

    它需要细节时，自己用只读工具去看代码和 `git diff`。估计上下文在 3 万 token 左右，大约是完整分叉的四分之一。代价是：开发 session 刚刚在工具里看到的东西，它不知道，得自己重新去读。
  - **完整分叉也可能很便宜**：如果分叉时的参数和开发 session 完全一样（同一个模型、同一套工具、同样的 MCP），只靠权限来限制成只读，不去改工具列表，第一轮就可能命中开发 session 的缓存。那样读 11 万 token 只要两三美分。这一点要在实现时先做个小试验，看第一轮的 `cache_read_input_tokens` 是不是接近整段上下文。
  - **我定的做法**：Butler 自动选。
    1. 试验证明能命中缓存，而且开发 session 在缓存有效期内跑过（Claude Code 用的是 1 小时那档）：用完整分叉。
    2. 其余情况：用精简版。黄框上注明「精简上下文」，旁边放一个「用完整上下文重问」按钮。
    3. 每个黄框都显示这次讨论花了多少钱。不设上限，这是用户定的。
- 屏幕上的 xterm 被 /clear 清掉没关系，因为对话 tab 读的是 Butler 存的这份。
