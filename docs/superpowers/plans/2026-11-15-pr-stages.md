# PR 进度条 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal：** ticket 页、feature 总控页、epic 页各加一个能收起的「PR 进度」tab，显示每个 PR 走到 设计 → 开发 → 自我 review → CI → peer review → 合并 的哪一步，ticket 页下面有能单独收起的时间线。

**Architecture：** 只存观察到的原始事件（skill 调用、第一个 commit、push、CI 结果、review、评论、合并），存进新表 `pr_stage_events`。进度和时间线每次由纯函数 `derivePrStages` 现算，不另存"当前步骤"。事件有两个来源：hook（session 的 `--settings` 新加的 `PostToolUse` Skill matcher，加上 `UserPromptSubmit` 里的 `/skill`），以及 PR 监视每一轮对比前后状态。时间线里的说明直接读 `inbox_items` 里已有的 report。

**Tech Stack：** Electron + TypeScript，node:sqlite（`db/database.ts`），React 渲染进程，vitest，Playwright e2e。

**Spec：** `docs/superpowers/specs/2026-11-15-pr-stages-and-review-lessons-design.md`。只实现「第一件：PR 进度条」，「第二件：review 经验」另写计划。本计划里存下的评论原文就是第二件的素材。

## Global Constraints

- 界面字符串成对加：`src/renderer/src/strings.ts`（ZH）和 `src/renderer/src/strings-en.ts`（EN），`strings.test.ts` 会检查两边的键一样。
- README.md 和 README.zh-CN.md 成对更新。
- 新表只能在 `src/main/db/migrations.ts` 的 `MIGRATIONS` 末尾追加，已发布的条目不能改。
- gh 调用走 `tickets/gh.ts` 的 `runGh`（有超时、gh 不可用时返回 null、不抛错），并且走 `PrWatcher.gh()` 的并发上限（4 个）。PR 监视的轮询频率（`PR_FAST_MS` 60s / `PR_SLOW_MS` 300s）不变。
- 渲染进程不直接调 gh。数据通过 IPC 拿，`stateChanged` 之后重取（和 `useInbox` 一样，防抖 80ms）。
- 宁可显示"跳过"或"未知"，也不显示错的状态。hook 程序不是当前版本时，设计和自我 review 显示"未知"，不显示"跳过"。
- Copilot 的 review 不算 peer review。peer review 看拉回来的 reviews 列表，不看 `reviewDecision`。
- tab 和时间线都能收起，状态记在本地：tab 用 `PageTabs`，时间线用 `useCollapsed`。
- 提交信息最后一行：`Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`。
- 每个任务结束前跑 `pnpm -s typecheck && pnpm -s lint && npx vitest run <相关目录>`，全部通过。

## Review Focus

1. **没开"必须 review"的仓库**（`reviewDecision` 一直是 null）：有人批准后 peer review 应该显示完成；没人批准就合并，应该显示"跳过"，不能一直停在"进行中"。Task 3 有测试。
2. **只有 Copilot 留了 review、没有人 review 就合并**：peer review 是"跳过"，Copilot 的 review 只出现在时间线上。Task 3 有测试。
3. **同一个 review、同一个 CI 结果被 PR 监视看到很多轮**：每轮都会看到同样的数据，事件不能重复写，时间线不能出现重复的行。靠 dedupe_key 唯一约束，Task 2 和 Task 5 有测试。
4. **ticket 的分支改过**（`rowOf` 把旧行当作没查过）：旧分支的事件不能混进新分支的进度。事件按 `repo_id` 加分支存，derive 只取当前分支的，Task 2 和 Task 7 有测试。
5. **多仓库 ticket 的总控、修复 session 调了 skill**：事件挂到正确的仓库（总控挂到所有仓库，修复 session 挂到它修的那个 session 的仓库），不能丢。Task 6 有测试。

### Task 3: derivePrStages（核心状态机）

**Files:**
- Create: `src/main/prwatch/pr-stages.ts`
- Test: `src/main/prwatch/pr-stages.test.ts`

**Interfaces:**
- Consumes: Task 1 的类型，Task 2 的 `StageEvent`。
- Produces:
  ```ts
  export interface DeriveInput {
    ticketKey: string; featureId: number | null; repoId: number; repoName: string; branch: string;
    ticketCreatedAt: number;
    /** forRepo 的结果。 */
    events: StageEvent[];
    /** upperDesign 的结果。 */
    upperDesign: StageEvent[];
    /** 这个 ticket 的 report（inbox_items kind=report），已经按仓库筛好（session 的 repoId 等于这个仓库或为 null）。 */
    reports: { at: number; text: string }[];
    /** pr_watch 的当前行，没有为 null。 */
    pr: { number: number | null; url: string | null; state: "open" | "merged" | "closed" | null } | null;
    /** hook 程序是当前版本，能看到 skill 调用。 */
    skillTracking: boolean;
  }
  export function derivePrStages(i: DeriveInput): PrStagesView;
  ```

状态机：把 `events` 按 `at` 排序后从头走一遍。维护当前轮 `round`（从 1 开始）、当前所在步骤 `cur`，以及每一步的 `PrStageCell`。下表就是规则，测试按表写。

| 事件 | 条件 | 效果 | 时间线 |
|---|---|---|---|
| skill（design） | `cur` 还没到 dev | design=active | design_skill，detail=skill 名 |
| first_commit | — | design：有 design skill → done；没有，但 `upperDesign` 里有早于 `ticketCreatedAt` 的 → feature_level；都没有 → `skillTracking ? skipped : unknown`。dev=active，cur=dev | first_commit |
| skill（review） | cur ∈ {dev, self_review} | self_review=active，cur=self_review | review_skill |
| pr_opened | — | 只记时间线 | pr_opened |
| ci pending | 有 PR，cur ∈ {dev, self_review} | dev=done；self_review：active → done，todo → `skillTracking ? skipped : unknown`；ci=active，cur=ci | ci_pending |
| ci pending | cur ∈ {peer_review, merge}，并且上一步不是 failed | ci=active，cur=ci，同一轮（Copilot 评论后小改再 push 的情况） | ci_pending |
| ci failing | cur=ci | ci=failed | ci_failed |
| ci passing | cur=ci | ci=done；peer_review=active，cur=peer_review | ci_passed |
| push | cur 那一步是 failed（CI 失败或要求修改） | round+1；dev=active，cur=dev；self_review、ci、peer_review、merge 重置为 todo，round 记为新一轮 | push，back=true |
| push | 其他 | 只记时间线 | push |
| review who=copilot | — | 只记时间线 | copilot_review，detail=这个 review 的行内评论数 |
| review who=human，state=CHANGES_REQUESTED | — | peer_review=failed，cur=peer_review | human_changes，detail=login |
| review who=human，state=APPROVED | — | peer_review=done；merge=active，cur=merge | human_approved，detail=login |
| review who=human，state=COMMENTED | — | 只记时间线 | human_commented |
| review who=human，state=DISMISSED | — | 忽略 | — |
| review who=author 或 bot | — | 忽略 | — |
| merged | — | peer_review 不是 done → skipped；merge=done；之前没走到的步骤：todo → skipped | merged |
| closed | — | `closed=true`，状态不再变 | closed |

补充规则：
- 没有任何 first_commit 事件，但 `pr` 有 PR：在第一个 ci 或 pr_opened 事件时补一次 first_commit 的效果（时间用那个事件的时间，不进时间线）。
- 每个 report 按 `at` 插进时间线，stage 取那个时间点的 `cur`（还没开发就是 design），kind=report，detail=原文前 200 字。
- 每个 cell 的 `round`：这一步最后一次被置为 active、failed 或 done 时的 `round`。`at`：最后一次变化的时间。
- 没有任何事件：design=`skillTracking ? todo : unknown`，其余 todo。

- [ ] **Step 1: 写失败的测试**，每个用例造一组事件，只断言关键字段。用例：
  1. 完整走一遍：design skill → first_commit → review skill → ci pending → ci passing → human APPROVED → merged，六步都是 done，round 都是 1，时间线 7 条。
  2. 没有 design skill，`skillTracking=true` → design=skipped；`skillTracking=false` → design=unknown。
  3. upperDesign 有一条早于 ticketCreatedAt 的 → design=feature_level；晚于 ticketCreatedAt 的不算 → skipped。
  4. CI 失败后 push：ci failing 之后 ci=failed；再 push → round=2，dev=active，ci=todo，时间线那条 push 的 back=true。
  5. 要求修改：ci passing → human CHANGES_REQUESTED → push → ci pending → ci passing → human APPROVED；最后 peer_review=done、round=2。
  6. **Review Focus 1：** ci passing → merged（没有任何 human review）→ peer_review=skipped，merge=done。
  7. **Review Focus 2：** ci passing → copilot review → merged → peer_review=skipped，时间线有 copilot_review。
  8. who=author 的 APPROVED 不改变状态。
  9. closed → `closed=true`。
  10. report 插在 CI 那一步 → 时间线里 stage=ci、kind=report。
  11. 有 PR 但没有 first_commit 事件，第一个是 ci pending → dev=done，ci=active。
  12. ci pending 在 peer_review 进行中（不是 failed）出现 → cur=ci，round 不变。

**Files:**

**Interfaces:**
- Consumes: Task 2 的 `StageEvent`，Task 4 的 `PrStatus`、`PrComment`、`reviewerKind`。
- Produces:
  ```ts
  // pr-observe.ts
  export interface Observation { event: Omit<StageEvent, "id">; dedupeKey: string }
  /** 纯函数。prev/next 是 pr_watch 行（next 是这一轮写进去的），pr 是这一轮的 prStatus（没有 PR 或 gh 失败为 null），
   *  inline 是这一轮拉到的行内评论（没拉为 []），firstCommit 是 git 算出来的（有 PR 时用 pr.firstCommitAt）。 */
  export function prObservations(t: PrTarget, prev: PrWatchRow | null, next: Omit<PrWatchRow, "deliveredKey">, pr: PrStatus | null, inline: PrComment[], firstCommit: number | null, now: number): Observation[];
  // pr-watcher.ts，PrWatcherDeps 新加：
  gh: { prStatus; branchRuns; failedLog; reviewComments: typeof reviewComments };
  git?: { firstCommitAt: typeof firstCommitAt };
  stages?: { has(dedupeKey: string): boolean; add(e: Omit<StageEvent, "id">, dedupeKey: string): boolean };
  ```

dedupe_key 的写法（都以 `${repoId}:` 开头）：`first_commit:${branch}`、`opened:${number}`、`push:${sha}`、`ci:${sha}:${result}`、`review:${id}`、`comment:${id}`、`merged:${number}`、`closed:${number}`。

规则：
- 第一个 commit：`firstCommit` 不为 null 就产生（at=firstCommit）。
- PR 刚出现：`prev?.number == null && next.number != null` → pr_opened。
- push：`prev?.headSha` 不为 null、`next.headSha` 不为 null、两者不同 → push（at=now）。
- CI 事件只在 `next.number != null` 时产生：`next.ci` 是 pending / passing / failing，并且 `prev` 为 null，或者 `prev.ci` 不同，或者 headSha 变了 → ci（at=now）。
- 每个 review → review 事件（at=submittedAt，who 用 `reviewerKind`）。state 为 PENDING 的跳过。
- `pr.comments` 和 `inline` 里的每一条 → comment 事件。
- state 变成 merged / closed → merged / closed（at=now）。

PrWatcher 的改动：
- `read` 返回 `{ row, pr }`，`checkOne` 拿到 `pr`。
- 只要 pr 里有一个 review id，在 `stages.has("${repoId}:review:${id}")` 里查不到，就调一次 `reviewComments`（走 `this.gh()`）。
- 没有 PR，并且 `stages.has("${repoId}:first_commit:${branch}")` 为 false 时，调 `git.firstCommitAt(t.cwd, t.branch)`。
- `prObservations` 的结果逐条 `stages.add`；有任何一条新加进去的，这一轮最后 `notify()`（和现有的 `changed` 合并）。
- `stages` 或 `git` 没给时整段跳过，现有测试不用改。
